# SFMC 代码审查规范（Code Review）

审查平台底层包（`packages/*`、`modules/sdk/*`）及生态模块 `@sfmc-bds/*` 时，以软件工程五大原则作为硬性检验维度。各原则的系统期望与重构策略详见 [principles.md](principles.md)。

## 审查执行流程

1. **界定变更范围**：提取 Git Diff 范围，对照 `AGENTS.md` 校验所属包边界与职责划分。
2. **五原则对照检查**：逐项排查设计与实现，每项发现明确标注对应的“设计原则 + 严重级别”。
3. **缺陷修复策略**：对于证据充分、具备可验证性的 BLOCKER 与 MAJOR 问题，直接给出最小修复补丁或就地修正。
4. **输出审查报告**：严格依照下方模板整理输出；未发现高危问题时明确注明「未发现 BLOCKER/MAJOR」并列出已检验维度。

> **免检范围**：纯文本错别字修正、单纯文档排版与简单单行注释变更可免去完整审查报告流程。

## 五大原则落地期望

| 架构原则                   | SFMC 平台落地期望形态                                                                                            |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **DRY（单一真实来源）**    | 权限校验、HTTP Body 解析、lock/catalog 读写、默认配置均有且仅有一处权威实现                                      |
| **OCP（开闭原则）**        | 新功能通过注册表（Registry）、路由工厂、策略模式扩展现有接口，无需侵入既有核心流程                               |
| **DIP（依赖倒置）**        | 业务模块仅经由 SDK 公开 API 交互；各服务包保持独立内聚；CLI 仅做流程编排                                         |
| **LSP（里氏替换）**        | 单操作路由与 `/db/tx` 事务调用、HTTP service 与 `tx.call` 在 moduleId 校验、权限门禁与返回信封格式上保持严格一致 |
| **迪米特法则（最少知识）** | 模块间仅通过 manifest 声明的服务与公开 SDK 协作；API 路由仅依赖已文档化的契约字段                                |

## 问题严重级别判定

| 严重级别    | 判定标准与处理策略                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------- |
| **BLOCKER** | **严重阻断性缺陷**：涉及安全越权、数据丢失/污染、破坏公共契约或致命运行异常；合并前必须修复                         |
| **MAJOR**   | **核心设计原则债务**：明显违背五大设计原则、架构层级倒置、或存在可预见的维护隐患；应在当前阶段修复或建立 Issue 跟踪 |
| **MINOR**   | **局部代码优化建议**：命名规范微调、局部微小重复、注释补充或格式对齐；可择机优化                                    |

## 标准审查报告模板

```markdown
# 代码审查报告：<变更范围或 PR 标识>

## 审查结论

<建议合并 / 存在 BLOCKER 需阻断修复 / 建议优先处理 MAJOR 技术债>

## 阻断缺陷（BLOCKER）

### B1. <缺陷标题>

- **违背原则：** DRY | OCP | DIP | LSP | 迪米特法则
- **问题位置：** `文件路径:行号` 或 具体符号（函数/类名）
- **判定证据：** <问题描述与触发场景>
- **修复方案：** <已应用补丁说明 / 推荐 Diff>

## 主要问题（MAJOR）

### M1. <问题标题>

- **违背原则：** ...
- **问题分析：** ...

## 次要建议（MINOR）

### m1. <优化建议>

## 已覆盖检查项

- [ ] 架构边界清晰（服务独立运行、CLI 负责编排、模块严格经 SDK 调用）
- [ ] 接口信封与鉴权一致（校验 moduleId 归属、数据信封格式与权限门禁）
- [ ] 发布包变更契约（公开 API 与关键行为变更已附带 changeset）
- [ ] 自动化测试验证（单元测试通过，pnpm run verify 校验无误）
```

## 平台现行契约专项核查清单

- [ ] `bds-tools` / `db-server` / `qq-bridge` / SDK 具备独立调用与测试能力
- [ ] 业务模块依赖边界清晰：仅依赖 `@sfmc-bds/sdk` 与 `@minecraft/*`；跨模块通过 manifest + service/tx
- [ ] SQL 执行使用受信任标识：严禁拼接未转义字符串，统一使用 `sql()` / `raw()`
- [ ] 终端玩家消息输出遵循统一规范：使用 `Msg.*`
- [ ] 配置生命周期符合架构设计：平台 JSON 变更经重启生效；运行时 lock 仅做 enable/disable 启停控制
- [ ] 公开包 API 与行为变更有 changeset 记录；预发布采用 beta tag
- [ ] `packages/tools` 保持为仓内私有包（`"private": true`）
