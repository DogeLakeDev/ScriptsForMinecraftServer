# SFMC 架构审查五大原则细则

本规范对代码审查中的五大核心原则在 SFMC 平台架构中的期望形态与修复策略进行系统化定义。

## DRY（单一真实来源，Don't Repeat Yourself）

单一逻辑仅保留一处权威实现。鉴权校验、HTTP Body 解析、lock/catalog 读写、默认配置初始化等通用机制必须抽离为共享底层实现；各调用方直接引用既有模块，严禁跨文件、跨包平行拷贝代码。

## OCP（开闭原则，Open-Closed Principle）

对扩展开放，对修改关闭。新增能力应优先通过注册表（Registry）、路由工厂函数、策略映射表等模式接入，以插件化机制扩展现有对外接口，避免对既有核心主干逻辑进行侵入式的分支堆叠。

## DIP（依赖倒置，Dependency Inversion Principle）

高层策略不依赖低层实现细节。SAPI 业务模块与运行时脚本仅通过 `@sfmc-bds/sdk` 公开接口与宿主交互；底层服务（如 `db-server`、`qq-bridge`、`bds-tools`）保持完全内聚且具备独立调用与测试能力；CLI 工具仅承担运维流程编排职责。

## LSP（里氏替换，Liskov Substitution Principle）

同构调用与等价执行路径必须遵守完全一致的行为契约。例如：单操作 HTTP 路由与 `/db/tx` 批量事务调用、HTTP service 路由与事务内 `tx.call`，在 `moduleId` 校验规则、数据权限门禁、以及返回结果信封（Envelope）结构上必须严格对称；通过共享校验单元与测试套件固化契约。

## 迪米特法则（最少知识原则，Law of Demeter）

严格限制模块与子系统间的信息暴露面。业务模块之间仅通过 `manifest.json` 显式声明的服务暴露与公开 SDK 接口进行协作；HTTP 路由仅消费文档化约定的请求字段；各工程包之间仅通过标准的对外导出点（`exports`）交互，杜绝跨层直读内部私有状态。

## 审查与合并门禁策略

- **阻断性缺陷（BLOCKER）**：凡涉及安全越权、鉴权旁路、跨模块数据穿透/污染、破坏公共发布契约的问题，必须在合并前修复。
- **架构技术债（MAJOR）**：严重违背上述五大原则的实现（即便当前功能可勉强跑通）均判定为 MAJOR 级别，要求当期重构或建立跟踪 Issue。
- **正向保真与最小修复**：缺陷修复与重构方案应采用最小必要补丁，完整保留现行正确业务逻辑与预期功能。
